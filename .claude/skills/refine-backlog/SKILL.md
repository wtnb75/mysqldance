# refine-backlog

`BACKLOG.md` の `todo` の項目を調べ、ユーザーに聞いて仕様を確定し、`ready` にする。`ready` の項目は、`impl-backlog` が質問なしで PR の作成まで進める。ここでは**実装しない**（コードを変えない）。項目の形式は `mgmt-backlog` に従う。

## 手順

1. **対象を決める**: 次のどれかで決める。`done` の項目は対象外。`ready` の項目は、ユーザーが確定し直すと言ったときだけ扱う。
   - **ID の指定**（複数でもよい）: その項目。
   - **条件の指定**（「5件」「P2 を全部」など）: `task backlog:next N=<件数>` の todo 欄から、条件に合うものを上から選ぶ（「全部」は `N=999`）。
   - **指定なし**: `task backlog:next N=3` の todo 欄の 3 件（優先度が高く ID が小さい順）を、ID とタイトルの一覧でまとめて提案する。

   条件の指定と指定なしのときは、選んだ一覧を見せて、了承を得てから調べ始める（外す項目・足す項目があれば、その場で直してもらう）。
   - blocked の項目は、提案には出さない。ID で指定されたら確定してよい。ただし、仕様が依存先の実装の結果で変わるなら、`ready` にせず、そのことを伝える。
2. **読んで調べる**: 項目のブロック、設計書（`docs/superpowers/specs/`）の関連する節、関連コードを読む。台帳（`docs/review-decisions.md`）は全文を読まず、関連するファイル名や関数名で `rg` し、当たった項目だけを読む。完了した項目の仕様が要るときは、`rg -n -A 12 '^## B-NNN ' docs/backlog-done.md` で 1 項目だけ読む。実機で確かめられる事実（MySQL の挙動、ツールの有無など）は、聞かずにここで確かめる。
   - 1つの PR に収まらない大きさなら、確定せず、`mgmt-backlog` の「項目の大きさ」に従って分割を提案する。
3. **質問をまとめて聞く**: 調べても残る不明点のうち、次のものだけを `AskUserQuestion` で聞く（推奨案を先頭に）。
   - 検証できない受け入れ条件
   - 複数の案があり、好みや方針で決まるもの（フラグ名、既定値、互換性など）

   一般的な既定値で決められるものは聞かず、「前提」として決める。聞くことが無ければ聞かない。対象が複数のときは、全部を調べ終えてから聞く。1回の呼び出しは4問までなので、超える分は項目ごとに呼び出しを分ける。質問には項目の ID を入れる。
4. **記録して `ready` にする**: 対象のブロックだけを書き換える。
   - `- 仕様:` に、答えと前提を箇条書きで書く。前提には「前提:」を付ける。`impl-backlog` が着手時に確かめ直せるよう、前提は関数名やファイル名などの確かめられる形で書く。
   - 受け入れ条件を、確定した仕様に合わせて直す。
   - 概要には書き足さない（調査の経緯は書かない。要るなら設計書に書く）。
   - 見出しを `[ready|Pn]` にする。
5. **報告する**: `ready` にした項目と、確定した仕様・置いた前提を日本語で要約する。`ready` にしなかった項目は、その理由を伝える。

## 守ること

- 変更は `BACKLOG.md` の対象のブロックだけ。調査の結果を設計書に残すときは、その節だけ。
- commit はユーザーが求めたときだけ。別のセッションや worktree の `impl-backlog` が `ready` を見られるのは、`origin/main` に入ってからなので、報告でそのことを伝える。
- 推測で `ready` にしない。答えが得られなかった質問が残る項目は `todo` のままにする。
