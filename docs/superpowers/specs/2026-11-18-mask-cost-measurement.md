# マスクの変換コストの計測（B-201）

マスク（B-166 以降）は、行ごとに HMAC を計算し、JSON 列ではパースと再出力を行う。これがダンプの時間とメモリにどれだけ効くかを、製品のコードを変えずに測った。結果は「実装の項目を始める前の判断材料」であり、実装の仕様ではない。

## 結論

- **文字列の変換は軽い。** 32 バイトの文字列 1 セルで約 210 ns。3 列を変換しても 1 行あたり約 0.64 µs で、行が小さい表（`*_short`）でも 1.3〜1.9 倍、行が大きい表（`*_large`）なら 1.03 倍以下。メモリの割り当てはゼロ（256 B のセルを除く）。
- **（B-169 で本物に差し替えた。「B-169 の実測」を見ること。バイトを保つ方式で、2 KB のセルが約 6.5 µs、割り当ては約 3 倍。以下の 3 項目は仮実装（`encoding/json` で全体を読んで書き戻す方式）の測定で、判断材料として残す。）**
- **JSON の変換は重い（仮実装）。** 2 KB のセルで約 53〜57 µs、20 KB で約 540 µs（1 セルあたり、1 コア）。行の大きさに近い値を持つ表なら、1 コアで 3.1〜3.8 倍、8 並列（`GOGC=400`）で 1.5〜1.7 倍で済む（見積もり）。行が小さいのに JSON だけが大きい表では桁が変わる。
- **JSON の並列化は GC が効く。** `GOMAXPROCS` を増やしても、既定の `GOGC=100` では 2 並列（約 1.8 倍速）で頭打ちになり、4・8 並列ではかえって遅くなった。`GOGC=400` にすると 8 並列で約 3.2 倍速になった。割り当て（2 KB のセルで約 30 KB・689 回）を減らす実装が必要。
- 並列化に価値があるのは JSON を含むときだけ。文字列の変換は 1 コアで足りる（8 並列で 4.4 倍速になるが、元が小さい）。

## B-167 の実測（本物の `hash_keep_shape`）

B-167 で `hash_keep_shape` を実装し、`internal/maskbench` の文字列の変換を、このベンチマークの仮実装から本物（`mask.DefaultRegistry()` の `hash_keep_shape` の `Func`）に差し替えた。JSON の変換は B-169 で本物に差し替えた（次の節）。上の「(a) 文字列の変換」の表は仮実装の値で、本物は次のとおり（同じ機材、`-count=3` の中央値付近。ns/セル）。

| 文字種 | 8 B | 32 B | 256 B | B/op、allocs/op |
| --- | --- | --- | --- | --- |
| ASCII | 218 | 450 | 2,900 | 24 / 96 / 768 B、3 |
| 日本語（6・30・255 B） | 185 | 282 | 1,500 | 24 / 96 / 768 B、3 |
| 絵文字 | 184 | 277 | 1,390 | 24 / 96 / 768 B、3 |

- 仮実装より遅い（32 B の ASCII で 212 → 450 ns）。理由は、1 文字につき 2 バイト（漢字は 3 バイト）のキーストリームを使い（仮実装は 1 バイト。剰余の偏りを小さくするため）、ブロックを 1 つ余計に作るため。キーストリームは、ブロック 0 を `HMAC(key, 値)`、以降を `SHA-256(ブロック 0 || 番号)` とし、長い値でも値の読み込みは 1 回で済む（256 B の ASCII は仮実装の 2,540 ns より少し遅い 2,900 ns）。
- 割り当ては 1 値につき、変換の中で 2 回（出力のバイト列と、結果の `sqlvalue.NewValue` が作るコピー）。ベンチマークの 3 回のうち残りの 1 回は、入力の `Value` を作る `NewValue`（変換の外）。コピーは `NewValue` の仕様（`database/sql` のバッファの再利用に備える）によるもので、所有権を渡す形にすれば減らせるが、`sqlvalue` の変更なので B-167 では行わない。
- 並列（32 B の ASCII）: 1 → 2 → 4 → 8 で 473 → 250 → 175 → 225 ns（8 並列は VM の 8 コアを MySQL と取り合うため、4 並列より遅い）。割り当てが小さい（値と同じ大きさの 2 つ）ので、JSON のような GC の競合は出ていない。
- 見積もり（外挿。3 列 × 32 B = 1.35 µs/行）: `int_short` 2.9 倍、`str_short` 1.7 倍、`int_large` 1.07 倍、`str_large` 1.05 倍。目標（文字列だけの変換は、行サイズが同程度の表で変換なしの 2 倍以内）は、行が大きい表では満たす。`int_short` の 2.9 倍は、行が極端に小さい表（目標の対象外）の例。ダンプに組み込んだ実測は未確認。

## B-169 の実測（本物の JSON パスの変換）

B-169 で、JSON 列のパスごとの変換（`internal/mask` の `jsonRewriter`）を実装し、`internal/maskbench` の JSON の変換を本物に差し替えた。測るのは、`$.user.email` に `hash_keep_shape` を掛けた 1 列の規則を、ダンプと同じ手順（`Parse` → `Resolve` → `Plan.Table`）で作り、1 行に当てる時間。仮実装（`encoding/json` の読み書き）は、比較のために `stdlib-roundtrip` として残した。同じ機材、`-count=3` の中央値付近。

| セルの大きさ | 本物（ns） | 仮実装（ns） | 比 | 本物の B/op、allocs/op | 仮実装の B/op、allocs/op |
| --- | --- | --- | --- | --- | --- |
| 約 200 B | 1,300 | 5,600 | 4.3 倍速 | 864、14 | 3,372、73 |
| 約 2 KB | 6,560 | 54,400 | 8.3 倍速 | 6,707、14 | 30,732、691 |
| 約 20 KB | 48,500 | 518,000 | 10.7 倍速 | 61,770、14 | 300,400、6,589 |

- **方式**: `encoding/json` で全体を読まず、バイト列を走査して、パスに当たる葉の範囲だけを差し替える。パスに入らない部分は、トークン（文字列、数値、`true` / `false` / `null`）の検査だけで読み飛ばす（割り当てなし）。書き換えない部分のバイト（キーの並び、空白、エスケープ、数値の桁）は元のまま。これは、仮実装の問題（キーの並びと空白の正規化、`<` `>` `&` の書き換え、根が配列やスカラーの JSON が読めない）を持たない。「JSON の変換（b）」の未決（許すか、バイトを保つか）は、バイトを保つ方式に決めた。
- **メモリ**: 1 セルあたり、セルの約 3 倍（ベンチマークの中で入力の `Value` を作るコピー、書き換えた文書の出力バッファ、結果の `sqlvalue.NewValue` が作るコピー）。ダンプでは入力の `Value` は読み出しが作るので、変換が増やすのは約 2 倍（出力バッファと `NewValue` のコピー）。仮実装の約 15 倍から減った。割り当ての回数は、セルの大きさによらず 14 回。
- **並列**（2 KB、`GOMAXPROCS` を 1・2・4・8）: 本物は 3.7 → 2.8 → 5.5 → 4.5 µs、仮実装は 46.4 → 28.4 → 41.0 → 62.4 µs。どちらも 2 並列を超えると伸びず、4 並列以上では悪化する（VM の 8 コアを MySQL と取り合う。割り当てが大きいほど GC が競合する）。ただし、最悪の点（5.5 µs）でも、仮実装の最良の点（28.4 µs）より速い。行の変換を並列にする（対策の案 1）は、この実装では要らない。なお `procs=1` の 3.7 µs は、単独の測定（6.5 µs）より速い。`GOMAXPROCS=1` では GC のワーカーも 1 つになるため、回収の競合が変わるのだと推測するが、確かめていない。
- **目標（行サイズが同程度の表で、変換なしの 3 倍以内）**: 既存の表（上の「変換ありのダンプ時間の見積もり」）から外挿すると、2 KB の JSON を 1 列変換する 1 コアの追加は、約 57 秒 / 100 万行から約 6.6 秒 / 100 万行になり、倍率は 3.1〜3.8 倍から約 1.2〜1.3 倍になる（`int_large` 20.3 秒と `str_large` 27.2 秒を基準にした見積もり。行の読み出しとの重なりは測っていない）。ダンプ全体の実測（実表で `--mask-rules` あり・なしを比べる）はしていない。目標のうち、1 セルあたりの時間とメモリ（2 KB で約 6.6 µs、約 3 倍）には収まる。
- **大きなセルの扱い**: 上限は設けない。仮実装は 1 セルあたりセルの 15 倍を割り当てたので、`MEDIUMTEXT`（16 MB）で約 240 MB と見積もっていたが、本物は約 2 倍（約 32 MB）で、`--jobs` 本の読み出しがそれぞれ 1 セルを処理する分だけ増える。`LONGTEXT` の JSON（最大 1 GB）は、MySQL の `JSON` 型の上限（`max_allowed_packet`）の範囲で、同じく約 2 倍。この外挿は、20 MB を超えるセルでは測っていない。

## 再現手順

```sh
# (a)〜(c) 変換の計測（DB は不要）
go test ./internal/maskbench -run '^$' -bench . -benchmem -count=3

# JSON の並列の伸びと GC の関係
go test ./internal/maskbench -run '^$' -bench 'Parallel/json' -benchmem -count=5
GOGC=400 go test ./internal/maskbench -run '^$' -bench 'Parallel/json' -benchmem -count=3

# ダンプ全体の基準（変換なし）
task sample:big ROWS=1000000
go build -o /tmp/mysqldance-bench ./cmd/mysqldance
time MYSQL_PWD=root /tmp/mysqldance-bench -h 127.0.0.1 -P 33072 -u root -o ./dump sample_big
task sample:down NAME=mysqldance-sample-big
```

`internal/maskbench` は `_test.go` だけのパッケージで、`go test -bench` のときだけ動く（`task test` はコンパイルするが、ベンチマークは動かさない）。`procs` が `runtime.NumCPU()` を超える行は skip する（8 コア未満の機材では `procs=8` の行は出ない）。今回の環境では `127.0.0.1:33072` に届かなかったため、コンテナの IP（`docker inspect`）に直接つないで測った。

## 計測するものの定義

- **文字列の変換（a）**: HMAC-SHA256（キーは固定、状態は goroutine ごとに使い回す）から、元と同じバイト長・同じ文字種の値を作る。数字は数字、英大小は英大小、ひらがなはひらがな（3 バイト）、絵文字は絵文字（4 バイト）に写す。キーストリームは 1 文字（rune）につき 1 バイトで、足りないときはカウンタを足して HMAC を繰り返す。UTF-8 として不正なバイトは、そのまま残す（長さを変えない。ベンチマークの中で `ab\xffcd` で確かめている）。
  - 測るセルの長さは、ASCII は 8・32・256 B、絵文字は 4 の倍数に切り捨てて 8・32・256 B、日本語は 3 の倍数に切り捨てて 6・30・255 B（表の見出しは 8・32・256 B）。
- **JSON の変換（b）**: B-201 の時点では、`encoding/json` で `UseNumber` を付けて読み（数値は読んだ文字列のまま保つ）、`user.email` だけを（a）で書き換え、`json.Marshal` で書き戻す仮実装だった（今は `stdlib-roundtrip` という比較の基準として残している）。この方式は、書き換えない部分も次のように変わる。B-169 で、バイトを保つ方式（トークン単位の書き換え）に決め、本物に差し替えた（「B-169 の実測」）。
  - キーの並びが辞書順になる。重複したキーは 1 つになる。
  - 空白とエスケープが正規化される。`<` `>` `&` は `<` などに書き換わる。
  - 根が配列やスカラーの JSON は読めない（`map[string]any` に読むため）。
- **並列（c）**: `b.RunParallel` と `GOMAXPROCS` を 1・2・4・8 にして、同じ仕事を回す。`ns/op` は 1 セルあたりの実時間なので、完全に伸びれば並列数で割った値になる。

## 結果

各値は `-count=3`（並列の JSON のみ 5）の中央値付近。

### (a) 文字列の変換（ns/セル、B/op、allocs/op）

| 文字種 | 8 B | 32 B | 256 B | B/op、allocs/op |
| --- | --- | --- | --- | --- |
| HMAC のみ（床。ASCII） | 96 | 96 | 196 | 0、0 |
| ASCII | 130 | 212 | 2,540 | 0、0 |
| 日本語（6・30・255 B） | 124 | 206 | 1,510 | 256 B、1（256 B のみ） |
| 絵文字 | 126 | 200 | 1,190 | 256 B、1（256 B のみ） |

256 B の ASCII で急に増えるのは、256 文字ぶんのキーストリームに HMAC を 8 回回すため（約 10 ns/バイト）。日本語・絵文字は 1 文字が 3〜4 バイトなので、文字数が少なく、HMAC が 3 回で済む。256 B の日本語・絵文字で 256 B・1 回の割り当てが出る理由は、調べていない。

### (b) JSON の変換（1 セルあたり）

| セルの大きさ | 読み書き全体（ns） | 読みのみ（ns） | B/op | allocs/op |
| --- | --- | --- | --- | --- |
| 約 200 B | 5,700 | 3,800 | 3,321 | 71 |
| 約 2 KB | 56,600 | 33,900 | 30,660 | 689 |
| 約 20 KB | 540,000 | 322,000 | 300,000 | 6,586 |

セルの 15 倍ほどが割り当てられる。速度は約 36〜40 MB/s。

### (c) 並列の伸び（ns/セル、小さいほど良い）

| 仕事 | 1 | 2 | 4 | 8 | 8 のときの伸び |
| --- | --- | --- | --- | --- | --- |
| 文字列 32 B（ASCII） | 213 | 110 | 77 | 48 | 4.4 倍 |
| JSON 2 KB（`GOGC=100`） | 52,800 | 29,300 | 41,200 | 61,000 | 0.9 倍（悪化） |
| JSON 2 KB（`GOGC=400`） | 46,400 | 26,000 | 15,700 | 14,500 | 3.2 倍 |

この表は、同じ VM の 8 コアを、MySQL（アイドル）と取り合いながら測った値で、`GOMAXPROCS` を変えると GC のワーカーも同じ数になる。ダンプの `--jobs N` とは同じではない。文字列の行は、再測定（キーストリームの長さを直したあと）で、初回の測定（198 / 98 / 50 / 32 ns）より遅く出ている。機材の状態でぶれるので、倍率は目安にとどめること。

JSON の並列は、割り当てが多いために GC が競合している。`GOGC` を上げると改善するのは、その裏づけ。メモリとの引き換えなので、製品に入れるときは `GOGC` の変更ではなく、割り当ての削減を先に検討すること。

## 変換ありのダンプ時間の見積もり

**外挿である。** 実際に変換をダンプに組み込んで測ったのではない。見積もりは「基準 + 列数 × ns/セル × 行数」で、変換が読み出しと重ならず直列に並ぶと仮定している。**1 コアの行は、重なりを無視した上限寄りの値**（実装が読み出しと変換を重ねれば、これより短くなる）。**8 並列の行は、下限寄りの値**（8 コアすべてを変換に使えると仮定していて、読み出し・書き出し・MySQL が同じコアを使う分は入っていない）。行数には比例するとして外挿している。

100 万行あたり。倍率は「変換なし」に対する比。

| 仕事 | 追加 | `int_short` | `str_short` | `int_large` | `str_large` |
| --- | --- | --- | --- | --- | --- |
| 基準（変換なし） | — | 0.72 秒 | 1.86 秒 | 20.3 秒 | 27.2 秒 |
| 文字列 32 B × 3 列 | +0.64 秒 | 1.9 倍 | 1.3 倍 | 1.03 倍 | 1.02 倍 |
| JSON 200 B × 1 列 | +5.7 秒 | 8.9 倍 | 4.1 倍 | 1.3 倍 | 1.2 倍 |
| JSON 2 KB × 1 列（1 コア） | +57 秒 | 80 倍 | 31 倍 | 3.8 倍 | 3.1 倍 |
| JSON 2 KB × 1 列（8 並列、`GOGC=400`） | +14.5 秒 | 21 倍 | 8.8 倍 | 1.7 倍 | 1.5 倍 |
| JSON 20 KB × 1 列（1 コア） | +540 秒 | 750 倍 | 290 倍 | 28 倍 | 21 倍 |

数億行の例: 3 億行の表に 2 KB の JSON 列が 1 つあると、1 コアで約 4.7 時間（57 µs × 3 億）、8 並列（`GOGC=400`）で約 1.2 時間（14.5 µs × 3 億）の追加。

### 読み方

- 行が小さい表（1 行が 1 µs 台）は、変換のコストが元の何倍にも見える。だが、そもそも 2 KB の JSON を持つ行は小さい行ではない。**比較すべき基準は、JSON のセルと同じ程度の行サイズの表**で、その場合は 1 コアで約 3〜4 倍、並列で約 1.5〜1.7 倍（見積もり）。注意: `*_large` は `BLOB` が 1 KB で、読む行は約 1 KB、出力は 16 進になって約 2 KB である。2 KB の JSON を持つ行（読む行が約 2 KB）とは、読む量が約 2 倍違う。同じ大きさの行の基準ではなく、「桁が同じ」程度の比較として読むこと。実際の目標の判定は、B-169 の実装後に、実表で測り直す（B-169 では、1 セルあたりの時間とメモリと、そこからの外挿までで、実表の実測はしていない）。
- メモリ: 文字列の変換は割り当てがゼロで、セルを 1 つずつ処理するため行を保持しない（計測では 0 B/op）。JSON は 1 セルあたり約 15 倍を割り当てる（20 KB のセルで 300 KB）。`--jobs` 本の読み出しがそれぞれ変換するので、「（変換中のセル × 15）× `--jobs`」程度（1 本が 1 行ずつ処理する前提で、並列の行変換（対策の案 1）を入れると、飛行中の行の数だけ増える。`GOGC=100` では生きているヒープの 2 倍までが目安）。**大きなセルでは、`MEDIUMTEXT`（16 MB）で 1 セルあたり約 240 MB、`LONGTEXT` の JSON（`max_allowed_packet` の範囲で、既定 64 MB、最大 1 GB）ではそれ以上となり、計測していない外挿である。** 大きなセルへの対策（上限を決めてエラーにする、など）は、B-169 で上限を設けないと決めた（本物は約 2 倍で済む。「B-169 の実測」）。

## 目標の提案

変換ありのダンプ時間を、**行サイズが同程度の表の、変換なしの 3 倍以内**にする（`--jobs` 既定、JSON を含む場合も含めて）。

- 文字列だけの変換: 2 倍以内。今の見積もり（`int_short` 1.9 倍が最悪）で足りる。実装は 1 コアの直列でよい。
- JSON を含む変換: 3 倍以内。仮実装では 1 コアで 3.1〜3.8 倍と、わずかに超えていた。B-169 の本物は、割り当ての削減（下記の案 2）で、約 1.2〜1.3 倍の見積もりになった（「B-169 の実測」）。
- 行が極端に小さいのに、JSON だけが大きい表は、この目標の対象外にする（元が速すぎて、倍率が意味を持たない）。代わりに、絶対値（セルあたり ns）で上限を決める。

## 目標を満たせないときの対策の案

1. **行の変換を goroutine で並列にして、順序を保つ。** 変換した結果を行の番号で並べ直して書き出す。出力は決定的なまま。JSON のとき 2 並列で 1.8 倍速だが、割り当てが多いと伸びない（上の表）ので、2 番と組にする。
2. **割り当てを減らす。**（B-169 で実装した。ただし `json.Decoder.Token` ではなく、バイト列を走査する方式）`map[string]any` に読まず、`json.Decoder.Token` で読みながら、パスに当たる文字列だけを書き換えて、そのまま出力に流す（キーの並びも保たれる）。`sync.Pool` で `shaper`・バッファを使い回す。
3. **JSON の部分的なパース。** 指定したパスのキー名のバイト列が、セルに含まれなければ、パースせずにそのまま出す。（B-169 では実装していない。走査は、パスに入らない部分を割り当てなしで読み飛ばすので、足りている）
4. **同じ値の結果のキャッシュ。** 値の種類が少ない列（国名、区分）は、HMAC の結果をキャッシュする。メモリの上限（件数）が要る。
5. **`GOGC` の調整。** 効果は大きいが、メモリを多く使う。最後の手段。
