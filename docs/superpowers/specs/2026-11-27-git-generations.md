# git による世代バックアップ（設計メモ）

状態: メモ（仕様は未確定。BACKLOG には未登録）

## 目的

出力ディレクトリを git リポジトリとして使い、ツール自身が commit・push・世代の整理まで行う。日次 N 世代、週次 M 世代のように保持数を指定できるようにする。

## 前提の整理

- blob は中身のバイト列だけで同一性が決まる。ファイル名・mtime・所有者は blob に入らない。ダンプが同じ中身を上書きしても差分にならず、変わらないファイルは世代をまたいで 1 つのオブジェクトを共有する。
- delta になるのは packfile にまとめたとき（`gc` / `repack` / `push`）。commit しただけでは、変わったファイルが丸ごと増える。delta の相手は到達可能な全オブジェクトから探すので、親子関係のないブランチ間でも効く。
- 出力は 1 レコード 1 行・内容ハッシュで区切るため、delta と相性が良い。

## 方針: 世代 = ブランチ

履歴の書き換え（force push）はしない。世代ごとにブランチを作り、古いブランチを消して gc する。

- 日次: `daily/YYYY-MM-DD`。同じ日の複数回の実行は、同じブランチに積む。
- 週次: `weekly/YYYY-Www`。日次の tip の tree を写した 1 コミット（squash 相当）。
- 保持数: `--keep-daily N`、`--keep-weekly M`（ブランチの本数で数える）。
- 削除の対象は `daily/` と `weekly/` で始まるブランチだけ。ユーザーのブランチやタグには触れない。

### 前の世代の子孫にしない

新しいブランチを前の世代の先頭から切ると、古いコミットに到達できてしまい、ブランチを消しても gc で消えない。必ず固定の root から切る。

### 共通の空 root コミット

- 空 tree（`4b825dc642cb6eb9a060e54bf8d69288fbee4904`）に対する親なしコミットを 1 つ作る。作成者・日時は固定（`1970-01-01T00:00:00Z`）し、どのリポジトリでも同じハッシュになるようにする。
- plumbing（`commit-tree`、`symbolic-ref`、`reset --soft`）で操作し、作業ツリーは触らない。`git switch` は使わない。

### 週次の作り方

`git commit-tree <日次 tip の tree> -p <root>` で 1 コミットを作り、ブランチをそれに向ける。`merge --squash` は使わない（3-way マージと作業ツリーの更新が入り、コンフリクトの可能性がある）。blob は日次と共有されるので、容量はほぼ増えない。

## 実行の流れ

1. ダンプ（既存の処理。全体を書き終えてから commit する）
2. 失敗時は commit しない。作業ツリーを前の状態に戻すかどうかは未決（README「Failure handling」と整合させる）
3. 世代の判定。必要なら新しい日次ブランチを root から作る（`reset --soft`）
4. `git add -A`、差分があれば commit。差分がなければ commit しない
5. 週次の昇格
6. 保持数を超えたブランチを削除（ローカルと、`--git-push` のときはリモートも）
7. `reflog expire --expire=now --all`、`gc --prune=now`
8. `--git-push` のとき push

## 実装の方針

- `git` バイナリを exec で呼ぶ。go-git は gc と repack が弱い。
- リポジトリが無ければ作る。`.gitignore` に `.mysqldance.lock` を足す。
- `.gitattributes` に `* -text` を書くか `core.autocrlf=false` にして、改行の変換で中身が変わらないようにする。
- 時刻は注入できるようにする（`--now` 相当。テストのため）。タイムゾーンは UTC に固定する。
- 出力ファイルの決定性は変わらない。commit の時刻はファイルの中身ではない。

## 注意点

- 世代の削除は個人情報の消去ではない。GitHub のフォーク、キャッシュ、リモート側の reflog に残る。マスク（`--mask-rules`）が前提。
- リモートの gc はツールの手が届かない。素の git サーバーは push のあとに `gc --auto` を走らせるが、閾値（loose 約 6700 個、パック 50 個）を超えたときだけで、到達不能なオブジェクトは 2 週間（`gc.pruneExpire`）残る。GitHub はメンテナンスの頻度が非公開で、PR の ref・フォーク・SHA 指定の URL からも見える。GitLab と Gitea は設定で housekeeping を調整できる。push された thin pack は補完されるだけで再最適化されないため、リモートの容量効率はローカルで `gc --aggressive` した状態より落ちる。ツールが保証するのは「ローカルで gc する」と「リモートのブランチを消す」までで、リモートの容量の回収と履歴の消去は保証しない。README にもこの範囲を書く。自前の bare リポジトリなら ssh 越しに `gc --prune=now` を呼ぶ手はあるが、ホスティングには効かない。
- 巨大ファイル: GitHub は 100MB 超を拒否する。`core.bigFileThreshold`（既定 512MB）超は delta の対象外。
- 分割テーブルのパート番号がずれると、名前ハッシュが変わり delta が効きにくくなる。
- delta の効きは `gc --aggressive`（window 250、depth 50）で上がる。`gc --auto` は loose が約 6700 個になるまで動かないので、明示的に呼ぶ。
- git はパーミッションを実行ビットしか覚えない。`--file-mode` の指定は復元時に残らない。
- 他の手段: 差分バックアップだけが目的なら restic や borg のほうが堅牢。git を選ぶ理由は、人が読める diff と、`docker-entrypoint-initdb.d` へそのまま使えること。
